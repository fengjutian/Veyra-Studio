# 空白文档 → 一句话 → 出图

> 状态：已交付（2026-11-10）。探针在 `packages/studio-web/visual/from-scratch-probe.ts`，
> 浏览器侧在 `packages/studio-web/harness/from-scratch.ts`。

## 一句话

编排循环证明了「AI 自己改设计」，视觉上下文证明了「模型看得见图」；这两件事合起来
仍留一个空档：**从一张白纸开始，一句话，能不能出一张设计稿**。这个探针补的就是
这个空档。

## 为什么空文档是另一回事

之前的验收都在**有内容的文档**上做（样例文档里已有一张对比度不足的文本）。
空文档没有现成的东西可以参照：模型得自己决定建什么节点、放什么坐标、填什么颜色、
层级怎么搭。前面那些能力一个都帮不上。

## 探针走的是产品同一条路

```
一句话 → Planner（仓库自己的提示与解析器）→ 命令计划
       → dry-run（领域校验）→ 结构审查 → 事务提交
       → 画布渲染（Canvas 2D）→ PNG
```

中间没有一步是探针自己实现的：计划用 `SafeAiEditor.createPlan`，提交用 `confirm`，
出图用 `capturePageScreenshot`——与「视觉上下文」给模型看图的是同一个渲染器，
出来的就是用户在工作台里看到的那张。

**为什么要能带反馈重试**：一次就成不现实，模型偶尔把字段写错，dry-run 会拦下来。
编排循环的做法是把报错回喂给模型让它改一版，这里照抄。回喂次数会被如实报出来——
「改了 2 版才成」和「一次就成」是两件事，不能混着说。

## 判据

| 检查项 | 判据 |
| --- | --- |
| AI 给出可落地的计划 | 计划里至少有一条命令 |
| 命令跑进真实运行时 | 文档里真的多了节点 |
| 页面不是空的 | 页面顶层有节点 |
| 出图非空 | PNG 里被画过的像素 > 0，且不同颜色 ≥ 3 |

最后一条不能省：**一张全透明的 PNG 也是「成功」写出来的**，但它什么都不是。
所以数的是「被画过的像素」和「不同颜色数」，不是「文件存在」。

## 凭据

真实模型那一跑需要端点与密钥，只从环境变量或 `--env-file=` 指定的文件读，
不写进仓库、不写进报告。两者都没有时用 `--stub` 跑确定性替身——
那只能证明「链路是通的」，**不能**证明「AI 会设计」，两者在报告里分开写。

```bash
# 真实模型
STUDIO_PROVIDER_BASE=https://api.minimaxi.com/v1 \
STUDIO_PROVIDER_MODEL=MiniMax-M3 \
STUDIO_PROVIDER_KEY=... \
npm run visual:from-scratch:probe -- --require-browser

# 或者从文件读（放在 .artifacts/ 下，该目录已被 .gitignore 忽略）
npm run visual:from-scratch:probe -- --require-browser --env-file=.artifacts/from-scratch/provider.env

# 确定性替身：只验链路
npm run visual:from-scratch:probe -- --stub --require-browser
```

产物落在 `.artifacts/from-scratch/`：`document.json`（最终文档）、`report.json`
（逐轮记录与判据）、`render.png`（出图）。

## 途中查出并修掉的三个真缺陷

这个探针不是白写的——它第一次跑就撞出三个互相叠加的问题，**每一个都足以让
「从零生成一页」在真实产品里必然失败**。

### 1. planner 的默认超时 60 秒，而整页计划要跑一分半

工作台建 planner 时没传 `timeoutMs`，用的是 `openai-planner.ts` 的 60 秒默认。
带推理的模型（MiniMax-M3）出一份整页计划实测 **84–124 秒**——
60 秒的预算把每次请求都掐死在半路。

流式救不了：超时计时器覆盖的是「从发请求到读完响应体」的总时长，
首字节来得再早也没用。

**改法**：超时做成设置项（`AiSettings.timeoutMs`，默认 300 秒，可夹在 10 秒–10 分钟），
工作台把它传给 planner。调长不会让快端点变慢，只是不再提前放弃。

### 2. 产品压根没设 `max_tokens`，预算不够时回复被截断在半路

工作台建 planner 时**没有传 `maxTokens`**，请求体里就没有 `max_tokens` 字段，
全靠服务端默认值兜底。一份整页计划本身就要上万 token——每条 `node.create` 都带
完整节点对象，推理模型还要额外烧一大截在思考上。

实测（MiniMax-M3，`max_tokens=8192`）：

```
finish_reason = length
completion_tokens = 8192（正好打满）
reasoning_tokens = 5572
```

计划写到一半被切断。**看上去像「模型不会设计」，其实是预算不够。**

**改法**：`maxTokens` 做成设置项（默认 32768，夹在 1024–128k），工作台显式传下去，
不再依赖服务端默认值。

### 3. 计划解析器锁定「第一个能 parse 的 JSON」，而不是「第一个是计划的 JSON」

被截断的回复里，残存的**单条命令对象**（`{"type":"node.create","payload":{…}}`）
本身也是合法 JSON。旧解析器只试到第一个能 `JSON.parse` 成功的候选就 `break`，
于是锁定那条残片，`normalizePlan` 抛「模型返回的计划缺少 summary」——
**模型明明给对了计划，错误信息却说它没给**。

这不只是报错难看：它把排查方向带偏了（去改提示词，而真正要调的是 token 预算）。

**改法**（`packages/ai-orchestrator/src/plan-parser.ts`）：

1. 候选的判定标准从「能 parse」改成「能 normalize 成一份计划」——不是计划就记下
   原因，接着试下一个候选；
2. 候选扫描递归下钻一层，外壳里包着真计划的情况（`{"plan": {…}}`）也能找到；
3. 识别**截断**：文本里有没配平的 `{` 时，报错明说「回复被截断：max_tokens 预算不够，
   或生成被中断」，不再报成「缺少 summary」。

## 实测结果

**MiniMax-M3（`https://api.minimaxi.com/v1`），需求原文「做一个登录页」**，
起点是一个空页面 `page:1`、零个节点：

| 指标 | 结果 |
| --- | --- |
| 尝试次数 | **1 次**（没有回喂重试，首版就过） |
| 耗时 | 181 秒（其中约 4.9k token 花在推理上） |
| 落地命令 | 39 条（`page.rename` + 37 × `node.create` + 1 × `text.patch`） |
| 文档节点 | 37 个，页面顶层 1 个 |
| 出图 | 960×680 PNG，652800 个被画过的像素，1564 种颜色 |

模型给出的计划：在空白文档里搭一张 1440×900 的中文登录页，含品牌介绍区、
邮箱与密码表单、记住我、忘记密码、社交登录与注册入口。

出图用的是工作台那套 Canvas 2D 渲染器，产出的就是用户在画布上看到的那张。

### 结构审查给出的两条警告（都不是缺陷，是该改的地方）

- 「计划会新建 37 个节点，改动范围偏大」——从零生成一整页就是这个量级；
- 「37 个节点使用了硬编码填充色，建议绑定颜色 token」——模型选了实色而不是 token。

第二条正是体检层的输入：下一轮自主运行会把它当成待修项回喂给模型，让它把颜色
绑到 token 上。这条链路是通的。

## 没做的

- **其它 Provider 没实测**：这一轮只跑了 MiniMax-M3。OpenAI / DeepSeek / OpenRouter /
  Ollama / vLLM / LM Studio 的出图能力没有验过。
- **没有做「一句话生成多页」**：只验了单页。多页流程（跨页一致性、补齐剩下的页）
  不在这条链路的覆盖范围内。
- **没有像素基线**：出图只断言「非空且颜色有层次」，没有逐像素基线——
  基线会绑死字体与抗锯齿，跨机器不可靠。
- **替身模式不证明任何设计能力**：`--stub` 跑通只说明链路没断。
