# 磁盘备份

> 文档状态：生效中的实现规格
> 建立日期：2026-11-09
> 关联文档：`current-project-status.md`、`project-progress-and-version-roadmap.md`（`0.2.0`）

## 1. 为什么还要磁盘备份

现有的三层保护都困在同一个浏览器里：

| 机制 | 解决什么 | 仍然怕什么 |
| --- | --- | --- |
| 事务日志 + 快照 | 崩溃恢复、撤销/重做 | 存储损坏 |
| 历史版本 / 重建基线 | 回滚到旧版本、回退到某一步 | 误删项目 |
| IndexedDB 自动备份 | 覆盖前留三份完整文档 | 清空站点数据、换浏览器、换机器 |

磁盘备份把完整文档写进用户自己选的目录：能跨浏览器、能进网盘/同步盘、
能直接拖回编辑器导入。**跨设备自动同步不在范围内**——那需要服务端或第三方
账号；同一份 JSON 放进用户自己的同步目录已经覆盖了大部分需求。**备份加密
已在范围内**（见 §7）：目录可能在网盘里、可能在别人能读到的共享盘上，
密文才是稳妥的默认形态。

## 2. 分层

```
disk-backup.ts          纯逻辑 + 可注入的目录端口（Node 里可测）
        ↑
disk-backup-browser.ts  File System Access API：选目录、权限、句柄持久化
        ↑
backup-crypto.ts        加密信封：PBKDF2 派生密钥 + AES-GCM（Node 里可测）
        ↑
disk-backup-panel.tsx   面板：备份到哪、上次何时、立即备份 / 断开、加密开关
        ↑
main.tsx                自动保存落盘后触发；目录句柄跨会话恢复
```

加密通过 `BackupContentEncoder` 端口接进执行器：`disk-backup.ts` 只管「什么时候
写、写到哪、留几份」，编码是另一件事，两者解耦，所以纯逻辑层照样能在 Node 里
用假编码器跑完整行为测试。

## 3. 纯逻辑

`DiskBackupRunner` 不抛错：自动保存链路上的备份失败不能把编辑器带崩，
失败写进状态由界面展示，且**不推进** `lastSavedAt`（下一次自动保存会重试）。

- **文件名**：`ufira-backup-<项目片段>-<UTC 时间戳>-r<revision>.json`。
  项目 id 折成 `[A-Za-z0-9._-]`，其余字符压成一个 `-`。时间戳定宽（`20261109T121957Z`），
  所以按文件名字典序排就是按时间排，轮转不需要读文件内容。
- **节流**：默认 5 分钟，第一次立即写；「立即备份」按钮用 `force` 绕过节流。
  与 IndexedDB 备份（10 分钟）各自独立：一边跳过不影响另一边。
- **轮转**：每个项目只保留最近 10 份。只处理**本项目**的备份文件——
  目录里用户的别的文件、别的项目的备份一律不碰。删文件不可逆，不能手滑。
- **状态**：`idle` / `disabled` / `throttled` / `saved`（带文件名与份数）/ `error`（带原因）。

## 4. 浏览器实现

- 只有 Chromium 系支持 `showDirectoryPicker()`；Firefox / Safari 上面板直接说明
  不支持，并指向「导出 JSON 备份」这条退路，而不是给一个点了没反应的按钮。
- 目录句柄可以结构化克隆，存在独立的 IndexedDB 库（`ufira-design-studio-fs`）里，
  下次打开自动恢复。
- **权限不能跨会话自动恢复**：页面加载时只能 `queryPermission()`，
  `requestPermission()` 必须发生在用户手势里。因此权限被收回后，
  要么重新点「立即备份」，要么重新选目录——界面不会偷偷弹权限框。
- 写入走 `createWritable()`（临时文件 + 原子替换），不会留下半截 JSON。
- 用户取消选择器（`AbortError`）是正常路径，不报错。

## 5. 验收

- 纯逻辑：文件名往返解析、非备份文件识别、轮转只删本项目最旧文件、
  节流边界、force 绕过、写入失败转状态且不推进时间、跨会话恢复节流。
- 手工（Chromium）：选目录 → 首次立即写一份 → 5 分钟内再保存不写 →
  「立即备份」立刻写 → 超过 10 份时最旧的被删 → 刷新页面后目录仍在、
  上次备份时间仍在 → 清空浏览器存储后目录里的文件仍在。
- 非 Chromium：面板显示不支持说明，不出现可点击但无效的按钮。

## 6. 备份加密

### 6.1 形态

加密是**显式开关**，默认关闭；开启后新写出的备份是密文，已经写出的明文备份
不会被追溯加密（要加密只能重新写一份）。

密文用 **PBKDF2-HMAC-SHA256**（210000 次迭代）从密码派生密钥，再用
**AES-GCM-256** 加密整份文档。选 AES-GCM 是因为它同时给完整性：密文被改过
一点就解不开，不会解出半截垃圾。

信封本身是 JSON，所以备份目录里仍然是一堆可读的 `.json`，拖回编辑器时按
**内容**判断是不是加密的，不按扩展名分家：

```json
{
  "format": "ufira-encrypted-backup",
  "version": 1,
  "kdf": { "name": "PBKDF2", "hash": "SHA-256", "iterations": 210000, "salt": "…" },
  "cipher": { "name": "AES-GCM", "iv": "…" },
  "data": "…"
}
```

- 每个文件用**新的 salt 与 IV**——复用 IV 会让 GCM 的安全性归零。
- 迭代次数写进信封：将来调高不会让旧文件解不开。
- 不认识的 `version`、缺失的 KDF 参数一律拒绝（**不猜**）。
- 信封里没有密码，也没有密码的哈希。

### 6.2 密码

**密码不落盘**：不进 `localStorage` / IndexedDB / 文档 / 备份文件，只在会话内存里
（`main.tsx` 里是一个 ref）。没有服务端就没有找回通道，**忘记密码就是永久丢失**——
这句话同时出现在界面上和本节里，不能只写在文档里。

密码输错时 GCM 认证失败，界面给的是「密码不正确，或备份文件已损坏」：GCM
分不清这两种情况，只说「密码错误」会把文件损坏误导成用户记错了密码。

### 6.3 导入

单个文件导入时识别加密信封并弹窗要密码，密码错了可以重试（最多三次）。
**批量导入不接受加密文件**：一批文件可能用不同密码，逐个弹窗会让「一次拖
十个文件」变成十轮问答，因此批量里明确失败并提示单独导入。

### 6.4 验收

- 纯逻辑（`packages/studio-web/test/backup-crypto.test.ts`）：加密解密往返、
  密文里搜不到明文、密码错解不开、同内容两次加密的 salt/IV 不同、迭代次数写进
  信封、只认结构不猜内容、base64 往返不丢中文与二进制字节。
- 执行器：装了编码器就写密文、编码失败转 `error` 且**不推进**节流时间、
  可以中途换掉编码步骤（开/关加密）。
- 导入：加密文件在批量里被明确拒绝（`project-import.test.ts`）。

## 7. 仍未完成

- **跨设备自动同步**：依赖用户自己的同步盘；没有账号、没有服务端。
- **定时后台备份**：只在自动保存真正落盘后触发；页面关闭时不会为了备份而阻塞。
