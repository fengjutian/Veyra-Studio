# 编排循环：让 AI 自己跑多轮

> 状态：已实现（2026-11-09）。代码在 `packages/ai-orchestrator`，工作台入口在
> `packages/studio-web/src/main.tsx` 的 AI 分段「自主运行」。

## 一句话

体检器（设计 lint、对比度、导出诊断）本来各自都能跑，缺的是把它们串起来的那一层。
编排循环就是这一层：**体检 → 计划 → dry-run → 审查 → 提交 → 再体检 → 再计划**，
直到没有待修项，或者撞上某条停止条件。

没有它，每一步都得人当鼠标；有了它，才谈得上「AI 自己跑一晚上」。

## 循环是体检驱动的，不是「把同一个需求问很多遍」

这是整层设计的关键。每一轮交给模型的输入里都带着**上一轮的体检结论**——
一份「哪里还不对」的清单，而不是用户当初那句话的复读。

```
第 1 轮：体检 → 发现 3 个待修项 → 模型改 → 重新体检 → 还剩 1 个
第 2 轮：把「还剩这 1 个」回喂给模型 → 模型改 → 重新体检 → 0 个 → 收敛
```

如果只是重复需求，模型每次看到的输入是一样的；第二轮之后它不会有任何新信息。
体检结论就是那个新信息。

## 体检层

`packages/ai-orchestrator/src/self-check.ts` 把三个来源聚成一份报告：

| 来源 | 检查什么 | 严重程度 | 是否算「待修项」 |
| --- | --- | --- | --- |
| `lint` | 硬编码填充/描边、未绑 token 的间距、不在栅格上、同级重名 | warning / info | 是 |
| `contrast` | 文本色与最近背景色的对比度是否达到 WCAG 阈值 | error | 是 |
| `export` | 导出时导不出去的特性（空布尔组、无几何的矢量、缺资源的图片） | error / info | 只有 `unsupported` 算 |

`approximated` 类诊断（椭圆渐变的旋转角丢失、组件实例只导物化子树）是**说明**
而不是缺陷：交付物能看，只是和设计稿有出入。报成缺陷只会让模型去做无意义的
改动，所以它们进报告但不算待修项。

### 指纹：判断「是不是同一个问题」的唯一依据

每条结论都有一个稳定指纹：

```
来源:代码#节点id        例：contrast:low-contrast#text:low
```

指纹**不含消息文本与数值**。对比度从 2.1:1 变成 2.3:1 时仍然是同一个问题
（还没修好），而模型每轮的说法都不一样——用消息比对会把「有点进展」误判成
「换了问题」。

## 停止条件

每一种都对应一件具体的事，界面直接显示是哪一种：

| 停止原因 | 含义 |
| --- | --- |
| `converged` | 体检没有待修项了，收工 |
| `max-rounds` | 轮次用完，但还有问题没修完（默认 6 轮） |
| `blocked` | 结构审查拦下了这次改动（删锁定节点 / 整篇还原 / 删页面） |
| `rejected` | 审批钩子否决了这次改动 |
| `no-changes` | 模型没给出任何命令 |
| `planner-error` | 模型调用或计划解析失败 |
| `execute-error` | 命令提交失败 |
| `cancelled` | 用户取消 |
| `oscillating` | 同一个问题反复出现且修不动 |

`no-changes` 与 `planner-error` 是分开的两件事：前者是模型的合法结论
（「我改不动」），后者是故障。模型回复里 `commands` 为空时，解析器抛的是
`PlanEmptyError`（继承 `PlanParseError`），编排循环据此分流。

## 震荡检测：模型在原地打转

同一个指纹**连续出现若干轮**（默认 3 轮）就判定为「修不动」：

1. 连续计数在每轮体检后更新——问题消失就清零，重新出现重新计数；
2. 判定修不动的指纹从交给模型的待修清单里剔除，模型不会再被要求修它；
3. 待修项全被判死时，循环以 `oscillating` 收尾。

这样「模型死活改不动这个问题」不会烧满轮次，也不会被当成「还有希望，再试一轮」。

## 回喂通道

体检结论通过 `AiPlanRequest.selfCheck` 传给 Planner，最终拼进提示的 **user 段**，
排在文档摘要**之前**——模型先看到「哪里不对」，再看「现在长什么样」。顺序反了
容易让它先通读文档再自己找问题（那就是在干体检的活）。

拼出来的样子：

```
体检结论（第 2 轮）：待修 1 项（错误 1、警告 0、提示 0）
本轮（第 2/6 轮）目标：针对下面列出的待修项逐项修复。
上一轮做了：把标题改成深色（落地 1 条命令）。
重新体检后还剩 1 项待修（比上一轮少 0 项）。
1. [错误][contrast/low-contrast] 文本「标题」的对比度 2.86:1，低于阈值 4.5（节点 text:low） —— 前景 #999999，背景 #ffffff

只针对上面列出的待修项做改动，不要顺手改其它节点。
```

轮次上下文放在体检结论里，**不放进「用户需求」**——用户需求是用户原话，
改写了模型就分不清哪句是命令、哪句是现状。

## 工作台用法

AI 分段新增「自主运行」区：

- 输入目标（复用「AI 指令」输入框），点「自主运行」；
- 轮次日志实时显示每轮摘要、落地命令数、待修项数量的变化；
- 收尾给出停止原因与说明；
- 运行中可点「取消运行」。

**每一轮都走正常事务**，所以跑完之后可以逐轮撤销——跑了六轮想退回第三轮，
撤销三次即可。

## 边界与限制

说清楚这一层**现在做不到什么**：

- **必须先配真实模型。** 产品把 AI 功能统一挂在「配好模型并启用」之后，没配模型时
  「自主运行」按钮是禁用的——演示规划器只在没有真实模型时兜底，界面上已经点不到它。
  所以这一层在真实模型缺席时是**用不了**，不是「跑了但没效果」。
- **模型看不懂体检清单就会空转。** 一份不针对清单的模型回复（每次都新建一张蓝卡片）
  修不好任何问题，循环会一路跑到停止条件，并如实报出「待修项没有减少」。这不是缺陷，
  是模型没有理解能力。
- **只修体检器能看见的问题。** 视觉上的问题（好不好看、排版对不对）不在体检
  范围内——那需要视觉上下文（截图 → 模型），是另一项能力。
- **导出诊断里的图片判定有边界。** 体检层只认「开跑前就声明在文档里」的资源：
  这些读不到字节才算真缺图；循环里新加的资源先给占位图，不误报。
- **单线程串行。** 每轮一次模型调用，六轮就是六次等待。真实 Provider 的延迟
  直接乘以轮次。

## 验收

- 单元测试：`packages/ai-orchestrator/test/autonomous-loop.test.ts`（15 项）——
  覆盖停止条件（收敛 / 轮次用完 / 震荡 / 阻断 / 空计划 / 审批否决 / 模型故障）、
  指纹稳定性与计数清零、体检结论确实回喂给了模型、每轮可撤销。
- 体检层与停止条件是**纯函数**，不碰模型也不碰文档，所以停止条件可以单独测。
- 端到端跑在真实的 `StudioProject` 上（内存仓库），断言的是最终文档而不是
  中间变量。
- 界面接线由 `npm run visual:loop:probe` 守着：真实界面上点「自主运行」→ 轮次日志逐轮
  显示落地命令 → 画布节点真的变多 → 如实报出停止原因。探针自带一个假的 OpenAI 兼容
  端点（用 `Page.addScriptToEvaluateOnNewDocument` 接管 `fetch`，按 SSE 协议回一份固定
  的计划），因此不依赖真实模型也能把整条链路跑通——产品要求配了模型才让用 AI 功能，
  探针不配就没法点「自主运行」。
