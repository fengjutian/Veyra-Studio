# 密钥作用域管理（口令加密落盘）

> 版本：0.6.0 · 落地日期：2026-11-10
> 状态：**已实现并有端到端探针验证**

## 为什么要有这个

密钥原来只活在标签页的 `sessionStorage` 里：关掉标签页就没了。

安全上这是对的——密钥不该长期躺在磁盘上。但实际用起来等于「没有」：

- 换一台设备、换一个浏览器，之前配好的端点和模型名还在（它们在 `localStorage`），**密钥没了**，
  用户得重新去服务商后台翻一遍；
- 每天关一次标签页，就要重输一次；
- 想在另一台机器上继续工作，只能口头/截图传密钥——比落到 `localStorage` 更糟。

所以这里补了另一条路：**用口令加密后落盘**。用户自己决定要不要开。

## 威胁模型

| 资产 | 存储 | 保护 |
| --- | --- | --- |
| 服务地址、模型名、启用开关 | `localStorage` | 明文（本来就不是秘密） |
| 密钥环（多把 + 当前下标） | `sessionStorage` | 随标签页消亡 |
| 密钥环（落盘副本） | `localStorage` 的 `studio:ai-key-vault` | **AES-GCM-256 密文** |
| 口令 | **不存** | 每次解锁重新输入 |

明确**不在**威胁模型内的：

- 拿到密文 + 同时拿到口令的攻击者（等价于拿到明文密钥，这是口令加密的固有属性）；
- 已经在浏览器控制台里执行任意 JS 的攻击者——他能读内存里的密钥，也能直接调用 Web Crypto。
  这是「密钥存在客户端」的固有属性，不是本方案引入的。

## 实现

`packages/studio-web/src/ai-key-vault.ts`：

- **加密**：AES-GCM-256，密钥由口令经 **PBKDF2-HMAC-SHA256 / 210,000 次** 派生；
- **盐**：16 字节随机；**IV**：12 字节随机，每次保存都重新生成；
- **明文载荷**：`{ keys: string[], activeIndex: number }`——存的是**环**不是一把，
  和 `sessionStorage` 里的格式一致，换设备后多把密钥和「使用中」的那把都还在；
- **记录格式**：`{ version, algorithm, kdf, iterations, salt, iv, ciphertext }`，全部 base64。
  带版本号是为了以后换算法时老记录能被认出来；
- **口令错了**：GCM 的认证标签校验失败，`openKeyRing` 返回 `undefined`——**不会解出半截数据**；
  密文被篡改同理。

### 为什么不做「记住口令」

「记住口令」等于把密钥明文放回磁盘，加密就成了摆设。所以每次开新标签页要输一次口令：
这是有意的取舍，不是没做完。

### 为什么用浏览器原生 Web Crypto

`crypto.subtle` 是浏览器原生能力，**没有新增任何依赖**。Node 24 也有同一套 API，
所以加解密逻辑在单元测试里跑的是**真加解密**，不是「假装加密」的替身。

## 界面

工作台 → 检查器 → AI 分段 → 「密钥落盘（口令加密）」：

| 控件 | 行为 |
| --- | --- |
| 口令输入框 | `aria-label="落盘口令"`，`autoComplete="off"` |
| 加密保存 | 用当前密钥环加密后落盘，**并把这把密钥环应用到当前会话** |
| 解锁载入 | 用口令解开磁盘密文，密钥回到会话；口令不对会明说 |
| 删除密文 | 清掉磁盘上的密文记录 |

状态提示走 `aria-live="polite"`，读屏器能听到。

「加密保存」顺带调用 `onSave(draft)`：用户加完密钥点它，期待的是「这会儿就能用了」，
而不是还要再点一次「保存设置」。

### 失败时明说

口令不对时提示是「口令不对（或密文已损坏）。」——**不静默失败**。静默失败会让人以为
「解锁了但模型还是不能用」，然后去查别的地方。

## 测试

### 单元测试（`packages/studio-web/test/ai-key-vault.test.ts`，8 项）

- 磁盘上只有密文，没有明文密钥；
- 口令对能解开，且拿回来的密钥和环结构一致；
- 口令错解不开；
- 密文被篡改解不开；
- 两次加密的密文不同（盐和 IV 每次重新生成）；
- 空密钥环 / 空口令报错；
- 能删除；
- 坏 JSON 当成「没有保管库」。

### 端到端探针（`npm run visual:vault:probe`）

单元测试能证明加解密本身对，答不了接线上的问题：磁盘上真的只有密文吗？新会话里密钥
真的能从磁盘载回来吗？口令错了会不会把界面卡死？

探针走**真实应用**（headless Chrome + CDP）：

1. 填一把密钥 → 设口令 → 「加密保存」；
2. 断言 `localStorage` 里有密文、**没有明文密钥**，`sessionStorage` 里有密钥；
3. **只清掉 `sessionStorage`** 再刷新（模拟「换个标签页」，磁盘密文留着）→ 断言面板里
   没有密钥、磁盘密文还在；
4. 口令错了点「解锁载入」→ 断言提示里有「口令不对」，且**没有**载入密钥；
5. 口令对了点「解锁载入」→ 断言密钥回到面板、`sessionStorage` 里也有。

CI 里作为 web job 的一步跑（`--require-browser`）。

## 探针的三个坑（写的时候踩的）

记下来是因为这几个都不是「代码写错了」，而是「仪表自己坏了」：

1. **按钮在视口外**：检查器面板比视口高，「添加」「加密保存」默认落在视口下面。
   直接按 `getBoundingClientRect` 的坐标派发鼠标事件会**点空**——探针一路报
   「磁盘上没有留下密文」，真因是坐标点在了空处。修法：先 `scrollIntoView` 再量坐标。
2. **滚完要等一拍**：`scrollIntoView` 之后布局还在滚，立刻量坐标会量到中间位置，坐标偏 30+ px。
   修法：滚 → `sleep(350)` → 再量。
3. **标记要清**：给按钮打 `data-probe-button` 标记来定位，下一次点别的按钮前不清旧标记，
   `querySelector` 会命中**上一次的按钮**。表现是「加密保存」点下去变成了「添加」。
   修法：每次点之前先 `removeAttribute` 掉所有旧标记。

## 没做的

- **真正的服务端密钥吊销**：客户端轮换只是「手里还有旧的那把」，不等于服务端已作废旧密钥。
- **多设备同步**：落盘是**本机**的。跨设备要用同一个口令各自落盘，没有同步通道。
  跨设备自动同步是 0.2.0 就明确搁置的跨设备方案，这里没有改变那个结论。
- **口令找回**：口令忘了就是没了，密文无法从任何地方恢复。这是有意的。
