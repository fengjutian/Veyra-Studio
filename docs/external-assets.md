# 外部素材服务：缓存、归因与退出策略

> 文档状态：生效中的实现规格
> 建立日期：2026-11-10
> 关联文档：`current-project-status.md`、`project-progress-and-version-roadmap.md`（`0.8.0`）、`asset-metadata.md`

## 1. 问题

外部素材服务指项目之外提供素材的服务：图标库、图库、设计系统商店。用户从这类服务
里拿一张图，会遇到三个问题，此前都没有答案：

- **同一个素材被反复下载**。用户插十张图标，服务被请求了十次；网络一慢，界面就卡住。
- **不知道这张图能不能商用**。作者与许可证只在服务自己的页面上，交付时没人记得去查。
- **想不用某个服务了**。服务涨价、下架、或者用户单纯不想再往那儿发请求——此时已经
  插进画布的图不能跟着裂开。

## 2. 数据模型

外部素材的记录挂在**资源元数据**上，不另建一张表：

```ts
interface ExternalAssetOrigin {
  provider: string;        // 服务标识，例如 "iconify"
  providerAssetId: string; // 服务内部的素材 id
  fetchedAt: string;       // 拉取时间（ISO 8601）
  expiresAt?: string;      // 缓存过期时间；缺省表示不过期
}

interface AssetMetadata {
  // ...
  origin?: AssetOrigin;    // 归因（人读的那份）
  external?: ExternalAssetOrigin; // 缓存键（机器读的那份）
}
```

四条约定：

- **缓存键是「服务 + 素材 id」两段**：只有 id 会在服务之间撞车（两个服务都有 `logo.png`）。
- **`origin` 与 `external` 职责不同**：`origin` 是用户可编辑的归因（作者、许可证、来源），
  `external` 是缓存键，改了它就等于换了身份。
- **不参与身份**：`external` 与 `hash` 无关，登记来源不改变资源内容。
- **随文档走**：存在文档里，因此 JSON 导出、备份、跨设备复制都带着它。

## 3. 缓存

缓存由**文档里的资源元数据**加**仓库里的字节**组成——不另建一套缓存存储，也就不会
出现「缓存和文档对不上」的情况。

取一份素材时（`resolveExternalAsset()`）：

1. 在文档里找 `external.provider` 与 `external.providerAssetId` 都对得上的资源；
2. 找到且没过期、字节也在仓库里 → **直接用缓存，不发请求**；
3. 找到但过期了 → 向服务重新取一次（拿到的还是同一个 id，字节变了就说明服务那边更新了）；
4. 没找到 → 向服务取。

缓存有效期由服务自己声明（`cacheTtlMs`），缺省永不过期。

**内容变了怎么办**：资源 id 是内容哈希推导的，服务那边更新了素材，重取之后字节变了、
资源 id 也跟着变，旧的那条元数据就成了没人引用的孤儿。重取的结果会带上
`supersededAssetId`，调用方据此清理——但**只在旧的那份没被节点引用时**才清（删了
会让文档立刻失效）。缓存查找取的是**最近拉取的那条**，不会一直命中过期的那份。

## 4. 归因

服务返回的归因信息写进 `AssetMetadata.origin`：

- `author` —— 作者 / 版权方；
- `license` —— SPDX 标识或一句人话；
- `source` —— 素材库名或原始 URL。

HTTP 服务的归因可以来自响应头（`x-asset-author` / `x-asset-license` / `x-asset-source`），
也可以在登记服务时填默认值兜底。

**归因不完整会出诊断**：服务声明了「要求归因」，但素材上没有作者或许可证时，导出
诊断会报 `external-asset` / `unsupported`——交付出去可能违反许可，这件事必须让人知道，
不能安静通过。

归因清单（`collectExternalAttributions()`）列出文档里每份外部素材的作者、许可证、
来源、引用它的节点，并可导出成 Markdown 随交付物附带。

## 5. 退出策略

用户可以「退出」某个服务——意思是**不再向它发请求**，不是「把已经用的东西删掉」。

退出之后：

| 情况 | 行为 |
| --- | --- |
| 本地有缓存 | 继续用缓存，界面与诊断标注「服务已退出，用的是本地缓存」 |
| 本地没有缓存 | 拒绝取用，**不会偷偷去请求** |
| 已有素材在画布上 | 不受影响——退出不该让已有设计裂开 |

彻底清理是另一件事，由用户显式发起（「清理缓存」）：`planExternalProviderPurge()`
先算出影响面——没被引用的素材可以清，仍被节点引用的只报告不动手（删了会让文档立刻
失效：图片节点指向不存在的资源）。

服务清单与退出清单存在 `localStorage`（刷新后还在），授权头只存在 `sessionStorage`
——它跟 AI 密钥一个待遇：磁盘上的明文令牌等于长期有效的凭证。

## 6. 工作台

「数据」分段新增「外部素材服务」区：

- 登记服务（标识、名称、地址模板、是否要求归因、缓存有效期、默认归因）；
- 每个服务一个「取素材」入口（填服务里的素材 id）；
- 每个服务一个「退出该服务」/「重新加入」开关；
- 「清理缓存」按钮（先看影响面再动手）；
- 归因清单（缺归因、已退出、缓存已过期都有标记）与「导出归因清单」。

## 7. 验收

- schema（`design-schema/test/external-assets.test.ts`）：外部记录能通过校验且不被
  zod 剥掉；provider / 素材 id 为空、拉取时间不是 ISO 时间戳都拒绝；本地素材没有
  这个字段完全合法。
- 运行时（`design-runtime`）：`asset.upsert` 拒绝空的 provider / 素材 id 与坏的
  时间戳。
- 服务逻辑（`studio-application/test/external-assets.test.ts`）：缓存命中不发请求；
  服务不可达时用过期缓存并说明；缓存过期会重新取；内容变了会重取并报出旧资源 id；
  同一条外部素材有多份记录时命中最近拉取的那条；退出后不再请求、已有缓存仍可用、
  没有缓存就拒绝；归因进清单、缺归因出诊断；清缓存时区分可清与被引用；HTTP 服务的
  素材 id 会编码、响应体有上限。
- 工作台设置（`studio-web/test/external-asset-settings.test.ts`）：授权头不落盘；
  服务清单与退出清单刷新后还在；退出只影响目标服务；读坏的存储不拖垮工作台。

## 8. 仍未完成

- **没有内置服务**：只提供机制与一个通用 HTTP 适配器，没有预置某个具体服务
  （Iconify、Unsplash 等）的现成配置——服务各自的鉴权与条款差异太大，不该由这里替用户决定。
- **MCP 侧没有暴露**：外部 Agent 不能通过 MCP 取外部素材。核心服务（缓存 / 归因 /
  退出策略）本身是 provider 无关的，MCP 工具能直接复用，但 MCP 的工具清单刻意保持
  很小，加一个「取素材」工具要先想清楚它的 scope 与审批语义。
- **归因不写进导出物本体**：HTML / SVG / PDF 产物里不带署名文本，只在诊断与单独的
  归因清单文件里给。
- **没有许可证合法性校验**：不检查 `license` 是不是合法的 SPDX 标识。
- **缓存不能跨项目共享**：缓存跟着项目走，同一台机器上的两个项目各存一份。
